# Завдання і контроль

## Стани
`NEW → IN_PROGRESS → DONE`, а також `CANCELLED`. Окремого кроку «на прийнятті» немає (ADR-0002).

| Дія | Хто | Результат |
|---|---|---|
| Розпочати | виконавець | `NEW → IN_PROGRESS` |
| Додати нотатку / % готовності | виконавець, автор, керівник, контролер | журнал `PROGRESS`/`COMMENT`; перша нотатка виконавця переводить `NEW → IN_PROGRESS` **із записом STATUS у журнал** |
| «Виконано» | виконавець; коментар — за бажанням | позначає частку виконавця (`TaskAssignee.doneAt`); завдання стає `DONE`, коли позначили **всі** активні виконавці (вимкнений користувач не блокує) |
| Змінити (назва, опис, термін, пріоритет, виконавці) | автор, керівник | лише відкрите; зняли останнього, хто не позначив, — `DONE` дією системи |
| «Повернути в роботу» | автор, керівник, контролер-користувач | `DONE → IN_PROGRESS`; **коментар обов'язковий**; частки виконавців скидаються; термін, що минув, треба замінити |
| Закрити достроково | автор, керівник | `→ DONE` з **обов'язковим коментарем** |
| Скасувати / відновити | автор, керівник | `→ CANCELLED` / `CANCELLED → IN_PROGRESS` |
| Видалити назавжди (ADR-0011/0012) | автор, адміністратор, директор | будь-який стан, зокрема на контролі; разом із журналом і сповіщеннями |

## Права (ADR-0012; ADR-0003 замінено)
- Хто що бачить — розділ «Хто бачить завдання» нижче; «керівник» у таблиці вище означає керівника, у чиїй вертикалі завдання, або директора чи адміністратора.
- Виконавець ставить завдання лише собі; іншим — керівник, директор, адміністратор.
- «Відкласти нагадування» — кожен, хто їх отримує: виконавець, автор, контролер.
- Брати на контроль і змінювати умови — керівник або сам контролер-користувач.
- Уся логіка прав — у `tasks/task.policy.ts` (чисті функції), сервіси лише викликають її.
- Невидиме завдання → **404**, не 403 (не розкриваємо існування). Права перевіряє сервер.

## Контроль
- Контролююча особа — рівно одна з трьох: **користувач**, **особа з довідника** (без акаунта), **вільний текст**. Окремо фіксуємо, **хто зареєстрував** контроль у системі (`controlSetById`).
- Поля: підстава (документ), інтервал нагадувань (або загальне налаштування).
- Контрольні завдання — завжди вгорі списків.
- Зняти контроль можна лише з відкритого завдання; сповіщаються контролер, хто реєстрував і виконавці.

## Журнал (хід виконання)
- Кожна зміна стану, контролю, терміну, виконавців — рядок у журналі.
- Дія системи пишеться **без автора** (`authorId = null`), а не від вигаданої особи.

## Атомарність
- Перехід стану — умовне оновлення: `updateMany({ where: { id, status: очікуваний } })` і перевірка `count === 1`, інакше `409 conflict`. Так два одночасні кліки не створюють двох переходів.
- Рішення, що залежить від **інших рядків** («чи всі виконавці позначили»), — лише після `taskRepository.lockForUpdate` на початку транзакції. Умовне оновлення тут не рятує: у READ COMMITTED два одночасні «Виконано» бачать одне одного незавершеними, і завдання лишається відкритим назавжди.
- Зміна завдання + журнал + скидання журналу нагадувань — в одній `$transaction`.
- Сповіщення надсилаються **після** коміту і не блокують відповідь.

## Тести
Кожне правило з таблиці вище — тест у `task-lifecycle.spec.ts` / `task.policy.spec.ts`, включно з негативними (чужий виконавець → 404, «Повернути» без коментаря → 400).

## Хто бачить завдання (ADR-0012)
- Адміністратор і директор — усі; керівник — вертикаль свого підрозділу (автор або хоч один виконавець у його підрозділі чи нижчому) + завдання, де він учасник; виконавець — лише свої.
- Будь-яку перевірку видимості чи прав робити лише через `task.policy` з `Viewer` (`viewerOf(req)` у контролері tasks): голий `User` без `scope` позбавляє керівника вертикалі.
- Нова дія із завданням = нове поле в `permissions()` + негативний тест для керівника чужої вертикалі.
