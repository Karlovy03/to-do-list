# ADR-0024: Моніторинг — відвідування й онлайн людей, стан сервера, лише для адміністратора

- Статус: прийнято (план і макети 49–55 погоджено власником) · 2026-11-28
- Доповнює ADR-0021 (живі оновлення), ADR-0009 (один образ)

## Контекст
Власник хоче, щоб **лише адміністратор** бачив, хто зараз у застосунку і хто й коли заходив, а також стан сервера: чи не забився він по пам'яті і що з ним зараз. Сервер — одна машина з 1 ГБ пам'яті і swap 2 ГБ; застосунок працює в Docker.

Рішення власника:
- тривог push-повідомленнями **немає**, стан видно лише на екрані;
- про відвідування пишемо **лише час** — без пристрою, браузера й IP;
- історію відвідувань зберігаємо **90 днів**;
- людям **не показуємо**, що адміністратор бачить їхні відвідування.

## Рішення
- **Лише адміністратор.** Маршрути `/api/monitoring/*` під `requireRole('ADMIN')`: директор, керівники й виконавці отримують `403`. У клієнті — вкладка «Моніторинг» в «Адмініструванні».
- **Онлайн — це відкритий застосунок,** тобто відкритий потік `/api/live`. Коли в людини відкривається перший потік чи закривається останній, live публікує сигнал `presence` лише адміністраторам.
- **Візит — неперервна активність людини.** Новий візит починається після перерви понад 30 хв.
  - Трекер після `requireAuth` пише у фоні, не частіше ніж раз на хвилину на людину.
  - Після перезапуску сервера трекер бере останній візит людини з бази.
  - Таблиця `Visit` має лише `userId`, `startedAt`, `lastAt`. Записи старші 90 днів щодня видаляються.
- **Стан сервера — з `/proc`.** У контейнері `/proc/meminfo`, `/proc/stat` і `/proc/vmstat` показують увесь VPS: пам'ять, swap, процесор і лічильник `oom_kill` (скільки разів ядро вбивало процес через нестачу пам'яті). Диск — через `statfs` тому шаблонів, це той самий диск VPS. Окремо показуємо:
  - застосунок: RSS, купа, затримка циклу подій;
  - базу: розмір, з'єднання, час відповіді;
  - файли шаблонів;
  - час останньої вдалої резервної копії (`backup.sh` пише його в `Setting`).
- **Сокет Docker не монтуємо:** це рівнозначно root-доступу до машини. Тому пам'ять окремо по контейнерах (база, Caddy) не показуємо.
- **Історія.** Знімок раз на 5 хв у `ServerSample`, зберігається 7 днів. Історія переживає перезапуск, тож видно, що було перед падінням. За тиждень на графіку — найгірше значення за годину, щоб не загубити піки.
- **Пороги «увага / погано»** — погоджено в макетах. Загальний стан — найгірший із показників.

  | Показник | Увага | Погано |
  |---|---|---|
  | Вільна пам'ять | < 15 % | < 7 % |
  | Swap | > 50 % | > 80 % |
  | Диск | > 80 % | > 90 % |
  | Процесор (середнє за 5 хв) | > 80 % | > 95 % |
  | Затримка циклу подій | > 200 мс | > 1 с |
  | З'єднання бази | > 80 % | — |
  | Файли шаблонів | > 80 % межі | > 95 % межі |
  | Резервна копія | старша 26 год або її немає | старша 3 днів |
  | Процес вбито через нестачу пам'яті (за добу) | — | хоч раз |

## Наслідки
- **Межа:** коли сервер лежить зовсім, застосунок не відкриється й нічого не покаже. Для цього потрібна зовнішня перевірка доступності (IDEAS).
- «Коли був» пишемо без роду: «щойно», «12 хв тому», «учора о 17:40». Роду людини система не знає.
- Візити — персональні дані. Мінімум полів, обмежене зберігання, доступ лише адміністратору.
- Push-тривоги, пам'ять по контейнерах, зовнішня перевірка — лише новим рішенням (IDEAS).
